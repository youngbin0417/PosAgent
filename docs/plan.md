# PosAgent 설계 문서

## 1. 문서 개요

### 1.1 목적

PosAgent는 기존 C/C++ 기반 시스템에 AI 에이전트 실행 흐름을 삽입할 수 있도록 지원하는 경량 그래프 런타임을 정의한다. 본 문서는 단순한 기획서가 아니라, 구현을 위한 설계 기준과 인터페이스 계약을 정리한 실제 설계 문서로 작성한다.

현재 코드 상태: Windows에서 그래프 정상 경로와 mock model -> registered tool -> model 왕복을 확인했다. OpenAI 호환 Chat Completions 어댑터와 Windows HTTPS 경로가 추가되었으나 실제 endpoint 왕복은 미검증이다. generic JSON Schema 검증도 미구현이다. 기능별 완료 상태는 `verification-status-ko.md`를 기준으로 판단한다.

핵심 목적은 다음과 같다.

- 기존 기능과 상태를 재사용하면서 그래프 기반 실행 루프를 구성한다.
- 모델 호출, 도구 실행, 조건 분기, 반복, 종료를 일관되게 처리한다.
- C/C++ 호스트와 직접 결합할 수 있는 공개 API를 제공한다.
- 초기 PoC 검증은 Windows를 우선으로 진행하며, Linux는 WSL을 통해 보조 검증한다.
- 첫 적용 분야는 제조 L2 기능이지만, 범용 그래프 코어 자체는 공정·설비에 종속되지 않도록 설계한다.

### 1.2 프로젝트 정의

- 프로젝트명: PosAgent
- 한 줄 정의: 이기종 C/C++ 시스템에 임베딩하는 경량 에이전트 그래프 런타임
- 주 사용자: 기존 C/C++ 시스템 개발자, 사내 AI 연계 개발자
- 기본 적용 환경: 제조 L2의 조업제어, 트래킹, 공정 모델, MES 연동, PLC 데이터 수집 연계
- 설계 목표: 기존 소프트웨어 자산을 활용하는 AI 작업자 개발 기반 확보

## 2. 배경 및 문제 정의

### 2.1 배경

현재 제조 L2 환경은 여러 기능이 분산되어 있다. 조업제어, 트래킹, 공정 모델, MES 연동, PLC 데이터 수집 등이 서로 다른 모듈로 존재하며, 대부분은 C/C++ 기반으로 구현되어 있다. 일부 모델 또는 외부 서비스는 Python 기반으로 구성되어 있어, 전체 시스템을 단일 언어·단일 운영체제로 전환하는 것은 현실적이지 않다.

이러한 산업 환경에서 AI 작업자를 도입하려면 단순히 자연어 응답 하나만으로는 부족하다. 실제로는 다음 단계가 필요하다.

1. 현재 상태를 조회한다.
2. 필요한 기능을 호출한다.
3. 결과를 해석한다.
4. 조건에 따라 다음 동작을 선택한다.
5. 종료 조건을 만족할 때까지 반복한다.

이 흐름을 각 시스템마다 개별적으로 구현하면, 모델 연결 코드, 도구 호출 규약, 상태 갱신 방식, 오류 처리, 운영 로그 정책이 모두 다르게 생긴다. MicroAgent-C는 이런 반복 비용을 줄이기 위해 공통 그래프 실행 기반을 제공한다.

### 2.2 문제점

다음 문제는 실제 구현에서 자주 발생한다.

- 각 프로그램마다 에이전트 루프를 직접 구현함
- 모델 응답과 기존 함수 호출을 따로 매핑해야 함
- 도구 인자 검증이 일정하지 않음
- 상태가 어디서 갱신되며, 어떤 시점에 복사되는지 불명확함
- 종료 조건과 오류 경로를 일관되게 추적하지 못함
- OS별 빌드 및 라이브러리 차이로 호환성이 떨어짐

### 2.3 설계 원칙

본 설계는 다음 원칙을 따른다.

- 작은 C 코어 유지: 그래프와 실행 상태에 집중하고 모델·플랫폼 의존성을 분리한다.
- 업무 비종속 설계: 공정 규칙, MES 로직, PLC 프로토콜을 코어 내부에 넣지 않는다.
- 명확한 소유권: 상태, 버퍼, 그래프, 결과의 생성 및 해제 책임을 명시한다.
- 공개 C 인터페이스: C 호스트와 C++ 래퍼에서 동일 API를 사용한다.
- 실행 권한 제한: 모델은 등록된 도구만 호출할 수 있고, 실제 실행은 검증된 코드 경로로만 수행한다.
- 점진적 확장: 순차 실행과 기본 에이전트 루프를 우선 검증하고, 이후 병렬·영속화 등을 확장한다.

## 3. 목표와 비목표

### 3.1 목표

- 사용자 정의 상태와 함수를 기반으로 에이전트 그래프를 구성한다.
- 일반 전이, 조건부 전이, 반복, 종료, 실행 제한을 지원한다.
- 기존 C/C++ 함수를 등록된 도구로 활용한다.
- 사내 LLM 및 외부 모델과 연결 가능한 어댑터 경계를 제공한다.
- OS별 차이를 코드 외부로 분리하여 공통 API를 유지한다.
- 기존 빌드, 디버깅, 운영 체계와 통합 가능성을 검증한다.

### 3.2 비목표

- 현재 L2 업무 전체를 LLM 기반으로 재구현하지 않는다.
- PLC 제어, 인터록, 고속 제어 루프를 대체하지 않는다.
- LLM 추론 엔진 자체를 개발하지 않는다.
- 기존 Python 모델을 C로 일괄 변환하지 않는다.
- 초기 버전에서 LangGraph의 모든 기능을 구현하지 않는다.
- 언어·OS 차이를 무시한 단일 바이너리 전략을 취하지 않는다.
- 첫 PoC에서 장비를 자율 제어하지 않는다.

## 4. 사용자와 개발 경험

### 4.1 사용자 역할

주 사용자는 다음과 같은 C/C++ 개발자이다.

- 상태 구조체와 데이터 흐름을 이해한다.
- 기존 함수와 IPC 호출 구조를 알고 있다.
- 도구로 연결할 수 있는 함수의 계약을 정의한다.
- 그래프 실행을 어느 호스트 컨텍스트에서 수행할지 결정한다.

### 4.2 개발자와 프레임워크의 분담

| 개발자가 정의하는 것 | 프레임워크가 담당하는 것 |
| --- | --- |
| 상태 구조체와 데이터 수집 방식 | 상태 참조를 노드에 전달 |
| 노드 함수와 갱신 로직 | 노드 실행 및 결과 처리 |
| 분기 조건 | 조건부 전이와 다음 노드 선택 |
| 기존 기능을 감싼 도구 함수 | 도구 조회 및 콜백 실행 |
| 허용 도구와 인자 범위 | 등록된 계약에 따른 호출 |
| 업무별 종료 조건 | 종료 코드와 실행 제한 처리 |
| 기존 로깅/운영 정책 | 추적 이벤트를 호스트 콜백으로 전달 |

### 4.3 기본 사용 흐름

1. 업무별 상태 구조체를 정의한다.
2. 상태를 읽고 갱신하는 노드 함수를 구현한다.
3. 그래프에 노드와 전이를 등록한다.
4. 모델이 사용할 도구를 등록한다.
5. 호스트가 적절한 실행 문맥에서 그래프를 구동한다.
6. 결과와 추적 이벤트를 기존 운영 체계로 전달한다.

## 5. 시스템 아키텍처

### 5.1 전체 구조

```text
기존 C/C++ 호스트 프로그램
│
├─ 업무별 상태 구조체
├─ 기존 업무 함수 / IPC 연결
├─ 업무별 어댑터
│
▼
MicroAgent-C 공개 C API
│
├─ Graph Core
│  ├─ Graph
│  ├─ Node
│  ├─ Edge
│  ├─ Conditional Edge
│  ├─ Run Context
│  └─ Termination
│
├─ Tool Registry
│  ├─ Tool Specification
│  ├─ Argument Validation
│  └─ Callback Execution
│
├─ Trace Hooks
│  ├─ Node Events
│  ├─ Tool Events
│  └─ Error Events
│
├─ Model Adapter
│  ├─ Request normalization
│  ├─ Response normalization
│  └─ Transport abstraction
│
└─ Platform Layer
   ├─ Time utilities
   ├─ Build/ABI handling
   └─ OS-specific wrappers
```

### 5.2 아키텍처 분리 원칙

MicroAgent-C는 다음 네 계층으로 구성한다.

- C 호스트 및 업무별 어댑터: 실제 애플리케이션과 기능 구현
- 공개 C API: 외부에 제공되는 표준 인터페이스
- 그래프 코어: 실행 루프, 상태 전이, 분기, 종료 처리
- 모델/플랫폼 어댑터: 외부 모델 및 OS 차이 분리

이 구조를 통해 동일한 그래프 코어가 다른 상태와 다른 도구 세트를 가지는 호스트에서 재사용될 수 있다.

## 6. 핵심 컴포넌트 설계

### 6.1 Graph

Graph는 구성된 노드와 전이 관계를 유지하는 정적 실행 정의이다. 구현 초기 단계에서는 다음 조건을 만족한다.

- 그래프는 빌드 단계에서 생성하고, 실행 중에는 구조를 변경하지 않는다.
- 노드와 엣지는 사전에 연결된다.
- 일반 전이와 조건부 전이는 그래프 정의에 포함된다.
- 순환 경로는 허용하지만, 무한 루프는 최대 실행 횟수로 제한한다.

### 6.2 State

State는 도메인별 데이터 구조이며, 호스트가 소유하는 구조체로 시작한다. 그래프는 상태를 읽고 갱신하는 참조 방식 또는 스냅샷 방식 중 하나를 선택한다.

권장 원칙:

- 상태 자체는 코어가 소유하지 않는다.
- 그래프는 상태의 포인터나 식별자만 참조한다.
- 상태 변경이 실시간으로 발생하는 경우, 업무별 어댑터가 스냅샷 또는 동기화 규칙을 적용한다.

### 6.3 Node

Node는 단일 작업 단위를 나타내는 콜백이다. 각 노드는 다음 정보를 가진다.

- 고유 식별자
- 실행 콜백 함수 포인터
- 사용자 문맥 포인터
- 입력 상태 참조 규칙
- 출력 상태 업데이트 규칙
- 종료 여부와 오류 처리 정책

초기 구현은 단일 실행 문맥에서 순차 실행을 지원한다. 병렬 실행은 후속 요구에 따라 확장한다.

### 6.4 Edge와 Conditional Edge

- Edge: 고정된 다음 노드 지정
- Conditional Edge: 현재 상태와 라우팅 콜백 결과를 기반으로 다음 노드 결정

조건부 전이는 다음 규칙을 따른다.

- 목적지 목록은 그래프 빌드 단계에서 제한한다.
- 조건 함수는 정수 또는 열거형 결과를 반환한다.
- 허용되지 않은 경로는 오류로 처리한다.

### 6.5 Run Context

Run Context는 실행별 상태를 저장한다.

포함 항목:

- 현재 노드
- 실행 횟수
- 시작 시각 및 경과 시간
- 마지막 오류 코드
- 취소 상태
- 현재 상태 스냅샷 또는 참조 식별자

### 6.6 Termination

종료는 다음 유형으로 구분한다.

- SUCCESS: 정상 완료
- ERROR: 노드 또는 도구 실행 오류
- MAX_STEPS_REACHED: 반복 제한 도달
- TIMEOUT: 모델 또는 도구 응답 지연
- CANCELLED: 취소 요청

호스트는 종료 코드를 기반으로 후속 조치와 로그 정책을 선택한다.

## 7. 데이터 모델과 공개 API 설계

### 7.1 핵심 데이터 타입

C에서 다음 타입을 기본으로 설계한다.

```c
typedef struct ma_graph ma_graph_t;
typedef struct ma_node ma_node_t;
typedef struct ma_edge ma_edge_t;
typedef struct ma_context ma_context_t;
typedef struct ma_tool_spec ma_tool_spec_t;
typedef struct ma_result ma_result_t;
typedef struct ma_trace_event ma_trace_event_t;

typedef int32_t ma_status_t;
typedef int32_t ma_node_id_t;
typedef int32_t ma_tool_id_t;
```

### 7.2 공개 API 설계 원칙

- 모든 함수는 C linkage로 노출한다.
- 구조체는 크기와 해석 규칙을 문서화한다.
- 라이브러리가 할당한 메모리는 라이브러리 API를 통해 해제한다.
- 반환값은 상태 코드와 결과 구조로 분리한다.
- 예외를 C 경계로 전파하지 않는다.

### 7.3 API 구성 예시

```c
ma_status_t ma_graph_create(ma_graph_t **graph_out);
ma_status_t ma_graph_destroy(ma_graph_t *graph);
ma_status_t ma_graph_add_node(ma_graph_t *graph, const ma_node_t *node);
ma_status_t ma_graph_add_edge(ma_graph_t *graph, const ma_edge_t *edge);
ma_status_t ma_graph_set_start(ma_graph_t *graph, ma_node_id_t node_id);

ma_status_t ma_context_create(const ma_graph_t *graph, void *state, ma_context_t **ctx_out);
ma_status_t ma_context_execute(ma_context_t *ctx, ma_result_t **result_out);
ma_status_t ma_context_destroy(ma_context_t *ctx);

ma_status_t ma_tool_register(ma_graph_t *graph, const ma_tool_spec_t *tool_spec);
ma_status_t ma_tool_invoke(const ma_tool_spec_t *tool_spec, const void *args, void *out, ma_result_t **result_out);

ma_status_t ma_trace_set_callback(ma_context_t *ctx, ma_trace_cb cb, void *user_data);
```

### 7.4 결과 구조

```c
struct ma_result {
    ma_status_t status;
    int32_t code;
    void *payload;
    size_t payload_size;
    char *message;
};
```

이 구조는 성공/실패와 연관 데이터를 함께 전달한다.

## 8. 도구 등록 및 실행 계약

### 8.1 도구 정의

도구는 다음 정보를 가진다.

- 이름
- 설명
- 인자 스키마 또는 필드 정의
- 허용 타입
- 필수 인자 목록
- 실행 콜백
- 결과 변환 규칙

### 8.2 실행 절차

1. 모델 또는 호스트가 도구 이름과 인자를 전달한다.
2. 등록 테이블에서 도구를 조회한다.
3. 인자 구조와 타입을 검증한다.
4. 허용 범위를 확인한다.
5. 해당 콜백을 실행한다.
6. 결과를 모델 또는 다음 노드에 전달한다.
7. 추적 로그에 호출 기록을 남긴다.

### 8.3 인자 검증 정책

초기 검증은 제한된 범위로 시작한다.

- 정수, 문자열, 부울, 배열 지원
- 필수값 검사
- 길이 제한
- 최소/최대 범위 검증
- 허용된 값 목록 검사

JSON Schema 전체 지원은 초기 버전에서 제외한다. 필요 시 이후 버전에서 확장한다.

## 9. 모델 어댑터 설계

### 9.1 목적

모델 어댑터는 외부 LLM 서버의 응답 형식을 그래프 코어가 이해할 수 있는 일관된 결과로 정규화한다. 그래프 코어는 모델 공급자에 직접 의존하지 않는다.

### 9.2 입력/출력 규칙

어댑터는 다음 형태의 결과를 생성해야 한다.

- final_response: 최종 사용자 응답
- tool_call: 도구 이름과 인자
- error: 실행 실패 또는 타임아웃
- stop: 종료 신호

### 9.3 외부 모델과의 경계

- HTTP, gRPC, 메시지 브로커, 기존 사내 게이트웨이 등 전송 구현은 어댑터 내부에서 처리한다.
- 도구 호출이 모델에서 지원되더라도 실제 실행은 등록된 도구 테이블을 통해 수행한다.
- 그래프 코어는 모델이 어떤 서버 구현인지 알 수 없도록 유지한다.

## 10. 실행 모델

### 10.1 기본 실행 흐름

```text
START
  -> 상태 준비
  -> 노드 실행
  -> 결과 확인
  -> 조건부 판단 또는 일반 전이
  -> 도구 호출 가능 여부 확인
  -> 다음 노드 선택
  -> 종료 또는 반복
END
```

### 10.2 실행 제어 규칙

- 매 실행마다 현재 노드, 상태 참조, 실행 횟수를 기록한다.
- 무한 루프를 방지하기 위해 max_steps 제한을 사용한다.
- 노드 실행 중 오류가 발생하면 즉시 종료 코드로 전파한다.
- 모델 호출은 타임아웃과 취소를 지원한다.
- 반복 실행은 호스트의 기존 스레드 또는 별도 실행 문맥에서 관리한다.

### 10.3 허용되는 초기 실행 모델

초기 버전은 다음 실행 모델을 기본으로 한다.

- 단일 스레드, 순차 실행
- 종료, 오류, 제한 조건을 명시적으로 처리
- 호스트가 호출을 제어하는 임베디드 방식

병렬 그래프, 멀티에이전트, 비동기 스트리밍은 후속 단계에서 확장한다.

## 11. 메모리와 소유권 모델

### 11.1 기본 원칙

- 상태는 호스트가 소유한다.
- 그래프는 구조와 메타데이터를 소유한다.
- 결과와 추적 이벤트는 라이브러리가 할당하는 경우, 라이브러리 API로 해제한다.
- 포인터를 포함한 구조체를 임의로 다른 프로세스로 전달하지 않는다.

### 11.2 메모리 복사 전략

Zero-Copy는 필수 조건이 아니다. 복사가 필요한 경우에는 다음 원칙을 적용한다.

- 작은 상태는 복사로 처리한다.
- 큰 상태는 호스트가 스냅샷을 정의한다.
- 구조체 안의 포인터는 라이브러리 밖에서 해석되도록 제한한다.

### 11.3 체크포인트와 복원

체크포인트는 우선 범위에서 제외한다. 향후 필요 시 별도 직렬화 계약을 설계한다.

## 12. 운영체제 호환 전략

### 12.1 목표

초기 PoC의 우선 검증 대상은 Windows이며, Windows에서 공통 그래프 코어와 도구 연동이 안정적으로 동작하는지 확인한다. Linux는 WSL을 사용해 보조 검증을 수행하고, 실제 사용자 환경에 따라 추가 검증을 확장한다. AIX와 HP-UX는 후속 지원 대상으로 둔다. 동일한 C API와 공통 코어 소스를 각 환경에서 빌드하고 실행하는 것이 최종 목표이지만, 이기종 환경 간 바이너리 호환성을 제공하는 것은 아니다.

### 12.2 지원 목표

| 운영체제 | 상태 | 배포 형태 | 검토 항목 |
| --- | --- | --- | --- |
| Windows | 우선 검증 대상 | DLL 또는 정적 라이브러리 | 호출 규약, 비트수, CRT 경계, 심볼 export |
| Linux (WSL) | 보조 검증 대상 | 공유 라이브러리 또는 정적 라이브러리 | 배포판, CPU, 컴파일러, 링커 옵션 |
| AIX | 후속 지원 목표 | 공유 객체 또는 정적 라이브러리 | OS 버전, 비트수, 심볼 내보내기 |
| HP-UX | 후속 지원 목표 | 공유 라이브러리 또는 정적 라이브러리 | PA-RISC/Itanium, 컴파일러, 라이브러리 형식 |

### 12.3 구현 방침

- C11 범위 내에서 공통 기능만 사용한다.
- OS별 기능은 플랫폼 계층에서 숨긴다.
- 특정 라이브러리 의존성을 강제하지 않는다.
- 외부 통신은 어댑터 경계 안에서 처리한다.
- 모델 전송 계층과 그래프 코어를 분리한다.

## 14. 보안 및 안전성

### 14.1 보안 원칙

- 모델은 허가된 도구만 호출할 수 있다.
- 실제 실행은 호스트 코드에서 명시적으로 검증한다.
- 민감한 데이터는 필요한 필드만 전달한다.
- 로그에 민감 정보가 남지 않도록 마스킹 또는 제한을 적용한다.
- 도구 호출은 인자 범위 및 필수값 검증을 반드시 통과해야 한다.

### 14.2 안전성 경계

- 그래프는 공정 제어나 PLC 직접 제어를 수행하지 않는다.
- 호스트는 작업의 안전상 필요한 정책을 별도로 유지한다.
- 라이브러리의 메모리 오류는 호스트 프로세스에 영향을 줄 수 있으므로, 폭넓은 테스트와 결함 경계 검사가 필요하다.

## 15. PoC 범위

### 15.1 PoC 목표

다음은 첫 번째 PoC의 목표 범위이며 현재 완료 판정이 아니다. 현재 완료된 범위는 최소 그래프 정상 실행과 별도 callback 호출까지다. 에이전트 통합 PoC는 아래 항목을 실제 코드와 테스트로 통과해야 완료로 본다.

- 그래프 실행기 기본 동작
- 상태 기반 분기
- 도구 등록과 인자 검증
- 모델 어댑터와 도구 호출 연동
- 다른 호스트에서 동일 코어 재사용
- Windows 환경에서의 빌드 및 실행

Linux는 WSL을 통해 보조 검증을 수행하며, Windows에서 공통 설계와 실행 모델이 검증된 후 확장한다. AIX와 HP-UX는 별도 검증 대상으로 유지한다.

### 15.2 Windows 우선 PoC 포함 항목

아래 표는 목표 검증 범위다. 완료 상태는 현재 상태 체크리스트에서만 관리한다.

## 19. 성공 기준

본 설계서의 성공 기준은 다음과 같다.

1. 동일한 그래프 코어가 서로 다른 호스트 상태와 도구를 재사용할 수 있다.
2. 모델이 등록된 도구만 호출하며, 실제 실행은 검증된 코드 경로를 통한다.
3. 호스트 프로그램과 라이브러리 사이의 메모리/수명 주기가 명확하다.
4. 확보한 환경에서 공통 소스 기반의 빌드와 실행이 증명된다.
5. PoC 수준에서 도구 요청, 상태 갱신, 분기, 종료를 실제로 관찰할 수 있다.

## 21. 최종 결론

MicroAgent-C는 단순히 AI 프레임워크를 만드는 프로젝트가 아니라, 기존 C/C++ 시스템을 AI 작업 흐름에 안전하게 연결하는 실행 기반을 만드는 프로젝트로 정의한다. 본 설계 문서는 공통 그래프 코어, 도구 등록 및 검증, 모델 어댑터 경계, 운영체제 호환성, 실행 제어 및 추적 정책을 모두 포함한다.

초기 목표는 큰 기능을 모두 구현하는 것이 아니라, 최소한의 그래프 실행기와 실제 도구 연동 시나리오를 통과하는 것이다. 이 PoC를 기반으로 하여 이후 확장, 이식성 검증, 운영 적용 여부를 판단할 수 있다.

이 문서는 기술 설계서로서 구현을 안내하는 기준 문서이며, 이후 코드, 테스트, 예제, 빌드 가이드를 보완해 최종 산출물로 발전시킨다.
